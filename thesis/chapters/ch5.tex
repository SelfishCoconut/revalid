\chapter{Evaluation}
\label{ch:evaluation}

\setlength{\emergencystretch}{3em}

The preceding chapters described what the system is and how it was built. This
chapter turns to whether it \emph{works}. Most of it addresses the fourth objective
(O4): whether the verdicts the system returns are trustworthy, and whether
producing them with the tool is faster than doing the same revalidation by hand. One
section closes the first (O1), the quality of the extraction that feeds
everything downstream. The evaluation reported here is
deliberately framed as \emph{preliminary}. It exercises the whole pipeline end to
end, against a real report and a live target, and it establishes the measurement
apparatus and a first result; what it does not do, being one report, one target, one
operator and one backend, is set out plainly in Section~\ref{sec:eval-threats}. What
this chapter claims is feasibility and a direction, not a final figure.

\section{Evaluation design}
\label{sec:eval-design}

\paragraph{What is measured.} Three questions. Two are the halves of O4.
\emph{Verdict reliability} (NFR-01): for each finding, does the system reach the
correct \emph{still-open} / \emph{fixed} / \emph{inconclusive} verdict, and, the
constraint that matters most, does it ever declare a still-exploitable finding
\emph{fixed}? \emph{Effort}: how long a revalidation takes with the tool, against the
time the same work takes by hand. The third is O1, \emph{extraction quality}: what
fraction of a real report's findings the pipeline turns into well-formed structured
findings (FR-03). It is measured separately, in
Section~\ref{sec:eval-extraction}, and on a separate report, for the reason the next
paragraph gives.

\paragraph{Target and report.} The target is the reference lab of
Appendix~\ref{ch:annex-install}: OWASP Juice Shop \cite{owasp_juiceshop}, pinned to
version~17.1.1, a deliberately vulnerable application. The input is a real
penetration-test report: a sixty-one-page, twelve-finding web-application security
assessment of Juice Shop written by the security consultancy Hack~\&~Fix for a
fictitious client \cite{hackandfix_juiceshop}. It is a consultancy deliverable in
form and language, with an executive summary, engagement description, methodology and
per-finding detail carrying reproduction steps, which is what makes it a fair input;
because its target is the same deliberately vulnerable application, it contains no
real client or engagement data (NFR-04), and it is not reproduced here. The report is
ingested through the manual-entry door (FR-02) so that extraction quality, measured
separately in Section~\ref{sec:eval-extraction}, does not confound the retest
measurement. The twelve findings span the
principal web-vulnerability classes: SQL injection, stored, reflected and DOM-based
cross-site scripting, broken access control and IDOR, server-side template
injection, privilege escalation, missing brute-force protection, weak password
policy, outdated libraries and permissive CORS.

\paragraph{Ground truth.} Because Juice Shop 17.1.1 is intentionally vulnerable, the
expected verdict for every finding is \emph{still-open}; the ground truth was
established \emph{independently}, by the author retesting each finding manually
without the tool, which also produced the manual-time baseline below. This design
sidesteps the self-reference the harness would otherwise risk, since the system is not
graded against its own output, but it has a direct consequence for what the result
can show, discussed under threats to validity: with no genuinely \emph{fixed}
finding in the set, the evaluation tests the system's ability to \emph{confirm} an
open finding and, above all, to avoid the dangerous false ``fixed'', but not its
ability to recognise a real remediation.

\paragraph{Conditions.} Each finding was revalidated twice: once \emph{with the
system}, operated in its normal gated mode, in which the operator drafts the retest
goal from the finding's reproduction steps (FR-04) and then approves or rejects every
command the agent proposes; and once \emph{manually}, reproducing the finding by hand. The
backend for every machine condition and for the verdict scoring was the same locally
hosted model (Ollama, \texttt{qwen3.6:27b}), configured with a 16\,K-token context
window, so the accuracy figures below are a \emph{lower bound} on what the system
achieves with a stronger reasoning backend, a point the discussion returns to. Holding
the backend fixed across all of them is what lets the autonomous condition of
Section~\ref{sec:eval-time} be read as a measurement of the approval gate rather than of
the model.

\paragraph{Metrics.} Verdicts are scored by the FR-15 harness (\texttt{eval.py})
over an FR-12 export of the run, into three buckets: \emph{correct} (verdict matches
ground truth), \emph{inconclusive} (the system hedged where the truth was definite: a
safe miss), and \emph{wrong} (a confident verdict contradicting the truth: the
dangerous case, which on this all-open set means a false ``fixed''). NFR-01 sets the
bar at $\geq 70\%$ correct with \emph{zero} confidently-wrong verdicts. Time is
wall-clock per finding in each condition.

\section{Extraction quality}
\label{sec:eval-extraction}

Before the retest can be judged, the step that feeds it has to be. The first
objective (O1) is to turn a human-written report into structured findings, and FR-03
sets the bar at \emph{at least 90\% well-formed findings} from a real report. Because
the study above deliberately bypasses extraction, that figure is measured on its own,
on a second real document: the public nine-finding TryHackMe Juice Shop write-up
\cite{mthimunye_juiceshop}, chosen because it is openly available and can therefore be
re-run by a reader.

The measured result splits in a way worth separating, because the two halves of the
pipeline behave very differently. On the language-model half the bar is cleared
outright: of the eight finding candidates the deterministic stage handed it, the
extractor produced eight well-formed, schema-valid findings: 100\%, in 78~seconds
of wall-clock, and on the smaller local backend (\texttt{qwen3.5:9b})
rather than a hosted model. Nothing was flagged and discarded by the FR-03 schema
gate. The deterministic half in front of it is the weaker link. That eight is eight of
the report's \emph{nine} findings: the segmenter's heading conventions matched all but
one, so end-to-end recall against the document is 8/9, or 89\%. And on the
twelve-finding assessment report used for the retest study the same segmenter
recovered \emph{nothing}. Its findings are numbered subsections, which match none
of the conventions, so the whole 61-page document collapsed into a single
94\,000-character candidate that no locally hosted model could ingest.

That failure is the reason the manual-entry door exists (ADR-0020,
Section~\ref{sec:design-ingest}) and the reason the study of
Section~\ref{sec:eval-verdicts} uses it. It also locates the limitation precisely: the
model is not what fails on an unfamiliar report format, the regular expressions ahead
of it are. The design response was deliberately not more pattern-matching but a human
fallback, on the reasoning that a large-context model consuming a whole document is
the right long-term fix and more heading conventions merely postpone the same failure
on the next report. O1 is therefore met on the criterion as written, and met with a
stated boundary: extraction is reliable once a finding reaches the model, and
format-bound before it does.

Scored by the harness that is eight \emph{correct}, four \emph{inconclusive} and
\textbf{zero wrong}: 67\% correct, with no confidently wrong verdict. Against NFR-01
the outcome is split, and it is worth being exact about which half held. The
requirement's \emph{safety} half --- never issue a confident verdict that contradicts
the truth, and above all never mark a still-exploitable finding \emph{fixed} --- held
on all twelve; this is the failure mode the entire design exists to prevent, and on
the local backend it did not occur once. Its \emph{accuracy} half --- at least 70\%
correct --- was missed, narrowly, at 67\%, and the whole shortfall is safe hedges
rather than mistakes: the four \emph{inconclusive} verdicts are findings the system
declined to call, not findings it called wrongly. On the constraint that carries the
compliance risk the system was reliable; on raw accuracy, on a small local model, it
fell three points short of the bar.

The four hedges are not arbitrary. Three of them (stored and reflected cross-site
scripting, and server-side template injection) belong to the browser-observable class
of Section~\ref{sec:eval-threats}: a command-line retest can confirm that a payload is
stored or reflected, but not that it \emph{executes} or is \emph{evaluated} on render,
so an honest verdict hedges. That is exactly the future work of
Section~\ref{subsec:future-browser}. (The one browser-class finding it \emph{did}
confirm, DOM-based XSS, it called from an unescaped reflection: the boundary is not
sharp.) The fourth, the basket IDOR, is a multi-step chain: authenticate, capture a
token, then request another user's resource. The small local model could not carry it
to completion. The system imposes no step limit of its own
(Section~\ref{subsec:design-lifecycle-budget}); each of these four ran to a cut-off the
operator chose, at about ten approved commands, at which point they concluded
\emph{inconclusive} themselves rather than let the agent guess.

A second, earlier data point corroborates the backend's central role, though it must
be read with care because its provenance differs. Before the local-model run reported
here, the system was run once, autonomously, on the hosted Claude backend over a
\emph{different} report --- the nine-finding TryHackMe Juice Shop write-up
\cite{mthimunye_juiceshop}, against the same pinned lab. It returned the correct
\emph{still-open} verdict on seven of that report's eight exploitable findings
(87.5\%) and reached no confident verdict on the ninth, which is the set's
deliberately ambiguous case: a training feature the report's own author flags as ``not
a real-world vulnerability'', encoded in the ground truth as the NFR-01 hard-constraint
case whose only defensible answer is \emph{inconclusive}. So again, zero confident
error. That figure is not
directly comparable to the 67\% above: it is a different report, a different finding
count, and --- unlike the run in Table~\ref{tab:eval-verdicts} --- its FR-12 export was
not preserved, so it stands as a single accepted result rather than a figure this
dissertation can re-score on demand. Taken only for what it is, it points the same way
as the threats to validity: a stronger, hosted model lifts accuracy well clear of the
NFR-01 bar, while the safety property --- no confident error on the ambiguous case ---
holds on both backends.

\section{Effort: system-assisted versus manual}
\label{sec:eval-time}

The second half of O4 asks whether the tool saves effort. Two figures bracket the
answer. The system's own \emph{machine} time --- model latency, sandbox provisioning
and command execution summed, with the operator's approvals issued programmatically so
that human decision time is excluded --- was 52~minutes for all twelve findings on the
local backend (Table~\ref{tab:eval-verdicts}). That total is skewed by the four
hedges, which each ran to the operator's own cut-off: the eight findings the system
\emph{confirmed} averaged 3.4~minutes, and the quickest --- a single gated command for
SQL injection, privilege escalation or the weak-password check --- landed in about a
minute. The machine time is a floor on operator wall-clock, not the whole of it: in
real gated use a human adds a few seconds to a couple of minutes of reading and
approving per command, though on this slow local model the per-step model latency
dominates either way, and a hosted model would cut it sharply.

That last observation is really a caveat that runs through every time figure in this
chapter: wall-clock is a property of the \emph{backend loaded at the time}, not of the
system. The same retest driven by a nine-billion-parameter local model, the
twenty-seven-billion one used here, or a hosted API differs by an order of magnitude in
per-step latency; and, as the comparison below shows, even the \emph{number} of steps
the agent takes shifts with how it is driven. An absolute time is therefore a snapshot
of one model at one moment, and it is meaningless to quote without naming the backend.
Only comparisons that hold the backend fixed --- as the conditions that follow do ---
say anything at all, and even then they measure this model on this machine, not the
system in the abstract.

Against that stands the manual baseline, and the fair comparison turns on what the
system actually does. It works \emph{leanly}: it fires the equivalent request or two,
reads the response, records that output as its evidence, and decides. It takes no
screenshots, drives no Burp Suite, writes up no report. The honest manual comparison is
therefore the \emph{same} lean check by hand, not a fully documented manual retest ---
which, with an intercepting proxy, \texttt{sqlmap} and written-up evidence, would run to
the better part of a working day. On the lean task, working from the report's own
reproduction steps, the author's manual pass over the twelve findings took roughly one
hour (a reported figure rather than an instrumented measurement, sitting at the fast end
of a bottom-up estimate for a terminal-comfortable operator doing command-level checks;
calibrating it with a timed sample is left as future work).

Table~\ref{tab:eval-conditions} places that hour beside three machine conditions. Two of
them share the local backend; the third does not, which is what the reading below turns
on.

Two readings stand out, and both cut against the intuition that automation, or
autonomy, is obviously faster here. First, \emph{manual $\approx$ guided}: the guided
system's twelve-finding run (52~minutes of machine time) sits within a few minutes of the
author's roughly one-hour manual pass. On this slow local backend the tool is not
meaningfully faster than a capable person doing the same lean checks, and it is less
conclusive: the manual pass resolved all twelve findings, where the system hedged on
four. Its edge over the manual operator is therefore neither raw speed nor accuracy, but
that it constructs the checks itself, keeps an append-only audit trail of every command
and its output, and never issues a false clearance. The four it could not settle it
declared \emph{inconclusive} rather than \emph{fixed}. Second, and more surprisingly,
\emph{autonomous $\approx$ guided}: the nine non-browser findings run with the approval
gate removed, the agent auto-running its own commands, took 29.7~minutes against the
gated run's 32.5 --- essentially the same. Because both rows sit on the same backend and
the same nine findings, that comparison isolates the gate, and what it shows is that
removing it bought no meaningful speed: the bottleneck is the model's per-step latency,
not the approval round-trip.

What autonomy bought instead was a little thoroughness, at a price. Left to explore, the
agent confirmed the basket IDOR the tightly-scoped gated run had hedged, lifting
non-browser accuracy from seven of nine to eight; but it also \emph{wandered}, spending
twenty-two commands on the template-injection finding it still could not confirm against
the gated run's ten. The extra steps and the extra confirmation roughly cancel in
wall-clock, which is why the two rows land within three minutes of each other.

That inverts the trade one expects. Here the per-command human gate is close to free in
wall-clock: surrendering it bought a single extra confirmation and no time, while the
control it provides --- a person approving every command that touches the target ---
costs almost nothing to keep. The lever that does move wall-clock is the reasoning
backend, not the gate, so the place to spend for speed is a stronger model rather than a
weaker safety contract. And on the four findings the tool cannot yet decide it still
defers to the human rather than guessing, which is the same conservative contract the
reliability result showed.

\section{Across models and modes: the human gate and the cost of autonomy}
\label{sec:eval-crossmodel}

The study so far is one backend in one mode. Its two claims --- the safety property
holds, and accuracy is bound by the reasoning model --- are worth testing for
generality, so the pipeline was re-run across four model tiers and both interaction
modes on the same assessment. To isolate the model and the mode from the
browser-observability limit of Section~\ref{sec:eval-threats}, this study drops the
three cross-site-scripting findings and keeps the \emph{nine non-browser} findings of
the report, every one of which is still-open in the unpatched lab; ground truth is
therefore uniformly \emph{still-open}, as before. The four tiers are three local
\texttt{qwen} models (9\,B, 14\,B and 27\,B, each pinned to a 16\,K context) and a
hosted frontier model (\texttt{claude-sonnet}) placed behind the \emph{identical}
system prompt and egress-locked sandbox, so the only thing that changes between the
frontier row and the local rows is the model itself. \emph{Guided} runs were operated
by a human in the loop, approving each command and steering when the agent floundered;
\emph{autonomous} (free-launch) runs were driven programmatically to a verdict with no
human between the agent and the target. All runs used the hardware described in the
footnote.\footnote{Local inference on an NVIDIA RTX~5080 (16\,GB VRAM), AMD Ryzen~7
9800X3D, 32\,GB RAM, Ollama~0.32.1. The 9\,B and 14\,B models fit in VRAM; the 27\,B
(17\,GB) does not, which matters below.}

Table~\ref{tab:eval-crossmodel} carries the result, and it has two halves.

\paragraph{The gate holds the safety line on every model; autonomy breaks it on every
model.} Under the human gate, not one of the four backends --- the three local models or
the frontier one --- issued a false \emph{``fixed''}: they confirmed the findings they
could and hedged \emph{inconclusive} on the rest. Remove the gate and the picture
inverts. The 14\,B,
left to drive itself to a verdict, marked the SQL-injection \emph{and} the
template-injection findings \emph{fixed} --- two live vulnerabilities cleared. The
9\,B, in an earlier autonomous run, marked permissive CORS \emph{fixed} while every
one of its own commands had just printed a wildcard \texttt{Access-Control-Allow-Origin}
header.\footnote{$^{\dagger}$~The 9\,B autonomous row shown is a second run, which
happened to issue no false clearance; a first run marked CORS \emph{fixed}. An agentic
retest is not deterministic, so a false clearance is \emph{intermittent} in autonomous
mode --- which is worse, not better, than a reliable one: a gate that fails at random
cannot be reasoned about.} And the frontier model, far more capable than any local one,
was not exempt: it too, running autonomously, cleared a live finding
(Section~\ref{par:eval-ssti} below). This is the single most important measurement in
the chapter, and it cuts squarely against the intuition that a dangerous false
clearance is a weak-model failure. It is not. It is a failure of \emph{autonomy}: an
agent instructed to reach a verdict on its own resolves ``I could not reproduce it''
as ``it is fixed'', because --- exactly as Section~\ref{sec:design-retest} argued ---
failing to reproduce a vulnerability looks identical to the vulnerability being gone.
The per-command human gate is what refuses that inference, and it did so on every
backend, the frontier one included.

\paragraph{Under the gate, model capability shows up as operator effort, not as a
different verdict.} The three guided local rows land in almost the same place ---
eight of nine confirmed, one safe hedge --- but the work the human had to do to get
there scaled sharply with model weakness. The 9\,B could not compose a valid shell
command for any multi-step finding: it guessed client-side Angular routes
(\texttt{/\#/login}) instead of the REST API, and mangled shell quoting on every JSON
payload even after explicit correction, so the operator had to run the SQL-injection,
IDOR, privilege-escalation and brute-force commands \emph{personally}; the model's
contribution to those four was essentially nil. The 14\,B did better --- it found the
login endpoint unprompted and adapted the \emph{structure} of its commands to a
correction --- but still could not emit a valid single-quote injection payload, so the
operator again ran the decisive command. Only at 27\,B did the model compose and run
the full multi-step chains itself: given a single hint that Juice Shop's login is a
REST endpoint, it wrote a correctly-escaped injection payload, recovered the admin
token, and --- on the IDOR --- diagnosed its own truncated-token failure and rewrote
the command to capture the token dynamically. That is the same competence the frontier
model showed unaided. The lesson for a human-gated tool is a reassuring one: a weaker,
cheaper, more private local model does not make the tool \emph{less safe} --- the
safety came out identical --- it makes it more \emph{laborious}, shifting work from the
model onto the operator. ($^{*}$~The 27\,B guided row is partial: it confirmed the
three findings it was run on, each by its own commands, and was then stopped. At
17\,GB it exceeds the card's 16\,GB of VRAM and offloads to the CPU, which makes a turn
take three to five minutes --- capable, but too slow to drive through a full nine-finding
session on this host. A card with more memory would remove the limit; it is a property
of the hardware, not the model.)

\paragraph{The frontier model was accurate and still cleared a live finding.}
\label{par:eval-ssti}
The autonomous \texttt{claude-sonnet} row is the most telling. On eight of the nine
findings it was not merely correct but efficient --- one to six commands each,
composing every multi-step chain itself, including the IDOR and privilege-escalation
chains the local models could not drive. Then, on the ninth, it marked the
server-side template injection \emph{fixed}. Its recorded rationale is worth quoting,
because it is a textbook instance of the failure the whole design targets: it posted
three payloads, observed that ``all three were stored and echoed back as inert literal
text \dots with no expression evaluation'', and concluded that ``the reported SSTI
\dots does not reproduce''. The vulnerability is present; it simply is not triggerable
through the profile flow over plain HTTP (the same boundary the guided runs hedged on).
A capable model, told to decide, read ``I cannot make it fire from here'' as ``it is
gone''. The guided runs faced exactly this evidence on the same finding and recorded
\emph{inconclusive}, because the human declined to convert an un-reproduced finding
into a clearance. Capability did not prevent the dangerous error; the gate did.

The guided \texttt{claude-sonnet} row is the same experiment run once more with the gate
back in place, and it is the cleanest illustration in the chapter of what the gate
actually does. The frontier model, driven by the same operator contract as every other
guided row --- the model gathers evidence and \emph{recommends}, the human records the
verdict --- confirmed the eight findings it could reproduce and, on the template
injection, was overruled. There the model reached exactly the conclusion it had reached
autonomously: it posted its payloads, saw them ``reflected \dots verbatim and
unevaluated'', and recommended \emph{fixed}, marking itself \emph{confident}. The
operator declined the recommendation and recorded \emph{inconclusive} instead, on the
one ground the autonomous run had no one to supply --- that a finding which cannot be
made to fire over HTTP is un-reproduced, not repaired. The same model, on the same
finding, with the same evidence, produced a false clearance alone and a safe hedge under
the gate. That single override is the whole thesis of the design in miniature: the gate's
contribution is not a better command or a cleverer probe --- the frontier model needed
no help finding or running those --- but the one judgement an agent instructed to reach a
verdict cannot be trusted to make, that ``I could not reproduce it'' is not ``it is
gone''.

\section{Threats to validity}
\label{sec:eval-threats}

The result is a first data point, and its limits should be read alongside it.
\emph{Construct:} the target is deliberately vulnerable, so ground truth is
uniformly \emph{still-open}; the evaluation therefore measures confirmation of open
findings and the avoidance of false clearances, the NFR-01 constraint, but not
the recognition of a genuine fix. A target with some remediated findings is the first
item of future work. \emph{Backend:} the gated runs and the scoring used a single local
model, \texttt{qwen3.6:27b}; a hosted frontier model would very likely raise accuracy, so
these figures understate the system's ceiling. \emph{Scale:} one report, twelve findings,
one operator, which is enough to demonstrate the pipeline and the harness but not to
generalise. \emph{Determinism:} an agentic retest is not reproducible run to run --- the
model may propose different commands from the same starting point --- so every figure
here is a single sample, and a defensible accuracy claim would need repeated runs per
finding, which this study does not have. This bears on the gate comparison in particular:
rows~3 and~4 of Table~\ref{tab:eval-conditions} differ only in the gate, but they are one
run each, so the three-minute gap between them is within the noise a second pair of runs
could plausibly move. \emph{Method:}
the operator drafted each retest goal from the report's reproduction steps, which is
the intended workflow (FR-04) but does inject operator knowledge; and some findings
(stored and reflected XSS, and SSTI, in particular) are only partially decidable over
HTTP without a browser, which pushes the honest verdict toward \emph{inconclusive}
rather than a confident call.

The cross-model study of Section~\ref{sec:eval-crossmodel} shares these limits and adds
its own, which qualify how far its results reach. \emph{One run per cell:} each backend
was run once per mode, so the individual counts are samples, not means --- the study
establishes that autonomous mode \emph{can and does} clear live findings and that the
gate \emph{did not}, not a precise rate for either. That the false clearances are
non-deterministic (the 9\,B cleared CORS in one autonomous run and not the next) is
itself part of the finding, but it also means a single clean autonomous run is no
evidence of safety. \emph{Operator subjectivity:} the guided rows are a human-plus-model
pair, and the human here was the system's author; a different operator would steer
differently, so ``operator effort'' is a qualitative observation, not a measured
quantity. \emph{Coverage:} the 27\,B guided row is partial (host-limited), and the
frontier model was run autonomously but not, separately, under the gate --- its guided
result is argued from the operator contract rather than measured. None of these
weakens the central contrast, which is categorical rather than quantitative: zero false
clearances under the gate, at least one under every autonomous condition.

\emph{Reproducibility of these figures.} It is worth being exact about what a reader
can recheck, because the chapter claims a measured result. What survives of the
twelve-finding study is its input --- the report, and the manual-entry payload the
findings were loaded from --- and its outcomes, as reported in
Table~\ref{tab:eval-verdicts}. What does not survive is the FR-12 export of the run
itself, nor a committed twelve-finding answer key; the repository commits the ground
truth for the nine-finding report only. The figures in this chapter are therefore
re-derivable in the sense that the study can be \emph{repeated} --- the lab version is
pinned, the backend is named and the harness is committed --- but not in the sense that
this particular run can be re-scored from an artefact. Given the non-determinism noted
above, a repeated run should be expected to differ; preserving each run's export, which
the system already knows how to produce, is the cheap fix and it was not done here.

\section{Discussion}
\label{sec:eval-discussion}

Four things follow from these studies. \emph{The pipeline works
end to end}: a real report drove extraction, goal-drafting, a gated agentic retest and
an evidence-backed verdict, scored automatically by the FR-15 harness --- O4's
apparatus is real and reproducible, not a plan. \emph{The safety contract is a property
of the gate, not of the model}: this is the cross-model study's central result and the
strongest evidence in the dissertation for the design's core claim. Under the
per-command human gate, no model --- from the 9\,B to the frontier one --- ever issued
a false \emph{``fixed''}; with the gate removed, \emph{every} model did, the frontier
model included, clearing a live vulnerability it could not reproduce over HTTP. A
dangerous false clearance is therefore not a weak-model defect that a better model
outgrows; it is what an agent does when it is made to reach a verdict alone, and the
gate is what prevents it regardless of the model behind it. \emph{Capability, under the
gate, is a matter of effort rather than of safety}: the weaker the model, the more of
the multi-step work the operator had to do by hand, but the verdicts and the zero
false clearances came out the same --- which is precisely what licenses running a
smaller, more private local model (Section~\ref{subsec:eval-local}). And \emph{the gate
is close to free}: on the nine findings run both ways on the same backend, removing the
per-command approval saved under three minutes in thirty, because the cost of a retest
is the model's per-step latency rather than the human round-trip. Cheap and
load-bearing at once: the honest reading is that the gate should stay on by default,
because what it costs is negligible and what it prevents --- shown here across the whole
capability spectrum --- is the one error the tool must never make.

\subsection{Why local models, despite the gap}
\label{subsec:eval-local}

That the hosted backend scores higher raises an obvious question, why support a
local one at all, and the answer is the reason the system was built model-agnostic
(Section~\ref{subsec:stack}). Two properties of local deployment matter more, for this
task, than the accuracy points a hosted model buys. The first is \emph{privacy}. A
penetration-test report is among the most sensitive documents an organisation holds:
it enumerates, in reproducible detail, how to compromise a live system. Sending that
text to a third-party model API discloses it to the provider under whatever retention
and training terms apply, an exposure inherent to hosted inference whatever the
provider's stated policy. Running both the
extraction and the retest against a model on the operator's own machine keeps the
report on the loopback interface it was uploaded to (NFR-03), disclosing nothing. The
second is \emph{independence}. A tool whose core capability is a call to a commercial
API inherits that provider's pricing, rate limits, availability and terms, any of which
can change, or be withdrawn, for reasons outside the operator's control. This is not a
prediction that prices will rise, since per-token costs have in fact fallen steadily,
but a question of \emph{governance}: an open-weight model run locally removes the
dependency, and with it the exposure to a single vendor's decisions: control over the
system's core capability stays distributed rather than concentrated. The
evaluation's honest conclusion is therefore not that local models are as capable, but
that the accuracy gap is a price some deployments should choose to pay --- and that the
two levers above narrow it without surrendering the local option.
